# Words Generator — проектный план

**Статус:** план разработки и техническая спецификация  
**Цель:** кроссплатформенное настольное приложение для генерации уникальных слов с помощью любой совместимой с OpenAI Chat Completions API языковой модели.

## 1. Назначение и основные принципы

Пользователь создаёт или открывает проект, выбирает язык и часть речи, подключает LLM через OpenAI Compatible API, задаёт количество слов и запускает генерацию. На каждый запрос модель должна вернуть ровно одно слово. Приложение проверяет ответ, сравнивает его с уже существующими результатами и добавляет только уникальные валидные записи в `words.txt`.

Ключевые принципы:

1. Один запрос к модели — один кандидат на слово.
2. Целевое количество — количество **новых уникальных слов текущей сессии**, а не размер ответа модели.
3. Уникальность и проверка формата выполняются локально; модель не является источником истины о повторах.
4. Каждое принятое слово немедленно записывается в UTF-8-файл.
5. GUI не выполняет сетевые запросы и длительные операции в основном потоке.
6. Настройки каждой сессии фиксируются на старте и не меняются вслед за редактированием глобальных настроек.
7. Проекты не содержат API-ключей и других секретов.
8. Приложение не привязывается к конкретному поставщику LLM или операционной системе.

## 3. Структура интерфейса

Главное окно содержит боковую навигацию и четыре страницы.

### 3.1. Проект

- Создание нового проекта и открытие существующего.
- Отображение имени, пути и числа уже сохранённых слов.
- Задание количества новых слов для следующего запуска.
- Кнопки запуска, паузы, продолжения и остановки.
- Отображение текущего состояния проекта и генератора.
- Открытие каталога проекта в системном файловом менеджере.
- Автоматическое сохранение настроек проекта.

### 3.2. Настройки

**Подключение LLM:**

- Base URL OpenAI Compatible API.
- API Key (не сохранять в каталоге проекта; использовать системное хранилище секретов).
- Идентификатор модели.
- Тайм-аут запроса.
- Получение списка доступных моделей через `/models`.
- Проверка подключения отдельным тестовым запросом.
- Профили нескольких подключений — последующее расширение.

**Параметры генерации:**

- Язык: предустановленные варианты и возможность пользовательского значения.
- Часть речи: существительное, глагол, прилагательное, наречие, местоимение, числительное или собственное значение.
- Редактируемый системный промпт.
- Кнопки готовых шаблонов: стандартный, строгий формат, разнообразная лексика, редкие слова.
- Кнопка построения промпта по текущему языку и части речи.
- Предупреждение перед заменой вручную отредактированного промпта.
- Сохранение снимка промпта в истории сессии.

**Сэмплер:**

| Параметр | Начальное значение |
|---|---:|
| Temperature | 0.9 |
| Top P | 0.95 |
| Frequency Penalty | 0.0 |
| Presence Penalty | 0.0 |
| Max Tokens | 24 |

Эти значения — стартовый профиль, не универсально оптимальные настройки для любой модели. Доступные параметры должны быть ограничены поддерживаемыми полями Chat Completions API. Должна быть возможность вернуть значения по умолчанию.

### 3.3. Статистика

Во время активной сессии отображать:

- целевое количество новых слов;
- добавленные слова и процент выполнения;
- отклонённые дубликаты;
- невалидные ответы;
- количество API-запросов и сетевых/API-ошибок;
- среднее время ответа;
- скорость генерации;
- продолжительность сессии и приблизительное оставшееся время;
- график скорости (по мере развития интерфейса).

Также нужен журнал событий с временными метками и фильтрацией: запрос, полученный кандидат, принятие, дубликат, невалидный ответ, ошибка, пауза, продолжение и завершение. Экспорт статистики — JSON/CSV.

### 3.4. История

- Список предыдущих сессий.
- Дата, использованная модель, параметры запуска и итоговый статус.
- Количество добавленных слов, повторов, ошибок и длительность.
- Просмотр журнала сессии.
- Повторный запуск с прежними настройками — последующее расширение.

## 4. Формат проекта и хранение данных

Рекомендуемая структура:

```text
MyProject/
├── project.json                 # метаданные и настройки проекта
├── words.txt                    # итоговые уникальные слова, UTF-8
├── history/
│   ├── session_<id>.jsonl       # события конкретной сессии
│   └── ...
├── state/
│   └── generation_state.json   # контрольная точка незавершённой сессии
└── backups/
    └── words_<timestamp>.txt   # резервные копии
```

`words.txt` содержит только слова: одна запись на строку, без нумерации, комментариев и метаданных. Секреты не включаются в `project.json` или журналы.

`project.json` содержит версию схемы, имя проекта, язык, часть речи, системный промпт, выбранный шаблон, целевое количество и параметры retry. Формат должен поддерживать миграции схемы при будущих изменениях.

Состояние сессии записывается атомарно во временный файл с последующей заменой. После каждого принятого слова файл результата синхронно сохраняется на диск; контрольная точка позволяет обнаружить незавершённую генерацию после аварийного завершения.

## 5. Генератор и обработка результатов

### 5.1. Цикл генерации

1. Загрузить множество нормализованных ключей из существующего `words.txt`.
2. Зафиксировать настройки сессии и создать файл журнала.
3. Сформировать запрос: язык, часть речи, системный промпт и требование вернуть одно слово без пояснений.
4. Отправить один запрос к Chat Completions API.
5. Нормализовать и проверить ответ.
6. Если ответ не соответствует формату — увеличить счётчик невалидных ответов и запросить новое слово.
7. Если нормализованный ключ уже существует — увеличить счётчик повторов и запросить новое слово.
8. Если слово уникально — немедленно добавить его в `words.txt`, обновить множество, статистику, журнал и контрольную точку.
9. Повторять до достижения точного количества новых уникальных слов, остановки пользователем или неисправимой ошибки API. Повторы и невалидные ответы не имеют лимита и не расходуют target.

### 5.2. Нормализация и уникальность

- Unicode NFKC для совместимого представления символов.
- Удаление внешних пробелов и внешней пунктуации.
- Сравнение через `casefold()`.
- Нормализация типографского апострофа для ключа сравнения.
- Поддержка внутренних дефисов и апострофов.
- Проверка дублей в старом файле и в текущей сессии.
- При совпадении сохранять только первоначальное написание.

### 5.3. Ограничение повторов и ошибки

- Дубликаты и невалидные ответы отклоняются без ограничения числа попыток: генерация продолжается до достижения target уникальных слов или ручной остановки.
- Отдельно учитывать дубликаты, невалидные ответы и API-ошибки.
- Сетевые ошибки и временные HTTP-ошибки повторять с экспоненциальной задержкой и ограничением числа повторов.
- Не завершать RUN из-за серии повторов: показывать их количество в статистике и оставлять доступной кнопку Stop. Сетевые/API-ошибки обрабатываются отдельным ограниченным retry-механизмом.
- Поддерживать отмену ожидания и корректную остановку.
- Пауза должна прекращать выдачу новых запросов; уже отправленный HTTP-запрос завершается или отменяется по тайм-ауту.

### 5.4. Проверка языка и части речи

Системный промпт направляет модель, а локальный валидатор проверяет структуру ответа и уникальность. Определение языка и части речи не может быть надёжно гарантировано одним регулярным выражением. Для строгой проверки в будущем можно добавить опциональные словари, морфологические библиотеки или отдельную классификационную модель. Такая проверка не должна незаметно отклонять редкие имена или слова, которых нет в словаре.

## 6. API-клиент

- `POST /chat/completions` — генерация одного кандидата.
- `GET /models` — запрос доступных моделей.
- Принимать Base URL с `/v1` и без него.
- Добавлять Bearer-токен только при наличии API Key.
- Валидировать JSON-ответ и понятным образом сообщать об ошибках HTTP, сети, тайм-аута и несовместимой схемы ответа.
- Не записывать API Key, Authorization-заголовки и полные секретные данные в логи.
- Предусмотреть настройки тайм-аута и минимальные retry для временных сбоев.
- Сохранять совместимость с OpenAI Chat Completions, не привязываясь к конкретному провайдеру.

## 7. Потоки и сигналы

Вся сеть и цикл генерации выполняются в `QThread`, а интерфейс обновляется через сигналы. Ожидаемые сигналы:

- `word_generated`
- `duplicate_rejected`
- `invalid_response`
- `progress_updated`
- `statistics_updated`
- `event_logged`
- `generation_paused`
- `generation_finished`
- `error_occurred`

Ядро генерации должно оставаться независимым от Qt, чтобы его можно было тестировать обычными unit-тестами.

## 8. Безопасность и надёжность

- API-ключ хранить через системный credential store (Windows Credential Manager, macOS Keychain, Secret Service в Linux); при недоступном backend не сохранять секрет открытым текстом без явного согласия.
- Не помещать ключи в проект, резервные копии, exception-тексты и журналы.
- Сохранять каждое принятое слово сразу.
- Делать резервные копии перед потенциально разрушительными операциями.
- Проверять повреждённые и неизвестные версии project-файла.
- Предупреждать о незавершённой сессии при открытии проекта.
- Защищаться от параллельного открытия одного проекта несколькими экземплярами приложения.
- Ограничивать объём журналов и давать возможность их очистки/экспорта.

## 10. Этапы разработки

### Этап 1 — фундамент

- Создать структуру Python-пакета и `pyproject.toml`.
- Настроить uv, pytest и Ruff.
- Создать точку входа и главное окно PySide6.
- Реализовать навигацию и базовую тему.

### Этап 2 — проекты и хранение

- Создание и открытие проекта.
- Чтение/запись `project.json` и `words.txt`.
- Автосохранение, история событий и контрольные точки.
- Резервное копирование и восстановление.

### Этап 3 — подключение LLM

- Реализовать OpenAI Compatible клиент.
- Настройки Base URL, API Key, model и timeout.
- Получение моделей и тест подключения.
- Параметры сэмплера и системный промпт с шаблонами.

### Этап 4 — ядро генерации

- Один кандидат на один запрос.
- Проверка структуры и нормализация.
- Дедупликация с существующим файлом и текущей сессией.
- Неограниченные повторы дубликатов/невалидных ответов до target уникальных слов, сетевой retry и немедленная запись результата.
- Unit-тесты ядра без реального API.

### Этап 5 — фоновая работа и статистика

- QThread worker, сигналы и управление задачей.
- Пауза, продолжение и остановка.
- Прогресс, показатели, журнал и история.

### Этап 6 — надёжность

- Восстановление незавершённых сессий.
- Обработка повреждённых файлов и сетевых ошибок.
- Блокировка одновременного открытия проекта.
- Тестирование на Windows/Linux/macOS.

### Этап 7 — релиз

- README и руководство пользователя.
- Иконка и полировка интерфейса.
- PyInstaller build-конфигурации.
- GitHub Releases для Windows, Linux и macOS.

## 11. Критерии готовности первой версии

- Приложение запускается на поддерживаемых ОС.
- Можно создать и повторно открыть проект.
- Можно проверить подключение к OpenAI Compatible API.
- Настройки языка, части речи, промпта и sampler сохраняются.
- Генератор запрашивает ровно один кандидат за раз.
- Повторы не попадают в `words.txt`, включая различия только в регистре или внешней пунктуации.
- Каждый успешный результат сохраняется сразу.
- GUI остаётся отзывчивым во время работы.
- Видны целевое количество, прогресс, повторы, невалидные ответы, запросы и ошибки.
- Секреты не попадают в project-файлы и логи.
- Основные операции ядра покрыты автоматическими тестами.

## 12. Версионирование реализации

Разработка ведётся небольшими проверяемыми этапами. Каждый этап должен завершаться рабочим состоянием репозитория, тестами и обновлением README. План является живой спецификацией: фактические изменения архитектуры необходимо отражать в этом файле.
